# M3.1: Push alerts through Bark

Why: ntfy.sh kept refusing requests from Render ("too many requests"), even with an account token. Render's free servers share addresses with other people, and ntfy limits per address. Bark worked when you tested it from n8n.

What changes for you:

- **Reminders and date alerts now arrive through the Bark app** instead of ntfy. Same timing rules as M3 (up to a minute early, 9 AM for date alerts).
- **The Google Calendar backup stays exactly as it was.** If a Bark push fails, one Calendar event replaces it, so there is still one alert.
- Everything about the chat router (workflow 01) is unchanged. Nothing to do there.

## 0. Check the chat router first

An early M3 version of the chat router created a Google Calendar event for every reminder. If you imported it, you get **two alerts** (Bark and Calendar). Open **01 Chat Router** in n8n. It must have **13 nodes** and none named *Calendar plan*, *Create event?*, *Create calendar event*, *Save event id* or *Delete calendar event*. If you see those, re-import `n8n/workflows/01-chat-router.json` from this repo:

1. Switch the old **01 Chat Router** off.
2. Import the file, choose the credentials (Jarvis token, Gemini key, Groq key, and Supabase on **Load context** and **Run SQL**), **Save**, **Activate**.
3. Delete the old router, and delete any test events it left in Google Calendar.

## 1. Update the repo

In PowerShell, from the folder that contains your `jarvis` folder:

```powershell
Expand-Archive -Path "$HOME\Downloads\jarvis-m3-1-update.zip" -DestinationPath . -Force
cd jarvis
git add -A; git commit -m "M3.1: push alerts through Bark"
```

## 2. Database (Supabase SQL editor)

1. Run `db/migrations/005_bark.sql`.
2. Save your Bark device key. It is the part of your Bark URL after `https://api.day.app/` (open the Bark app to see it). Replace the text and keep the double quotes inside the single quotes:

```sql
update jarvis.settings set value = '"your-bark-key"'::jsonb where key = 'bark_key';
```

3. Optional clean-up of your earlier tests (also delete the test events in Google Calendar by hand):

```sql
delete from jarvis.items where type = 'reminder';
```

The key is a secret. It lives only in this settings row, never in the workflow, the repo or a screenshot.

## 3. Replace the dispatcher in n8n

1. Open **02 Reminder Dispatcher**, switch it **off** (Active toggle), then delete it.
2. Import `n8n/workflows/02-reminder-dispatcher.json`.
3. Choose credentials:
   - **Claim due alerts**, **Record outcome**, **Find stale repeats**, **Save stale**: your Supabase credential.
   - **Backup event**: your **Google Calendar** credential.
   - **Bark**: nothing to choose.
4. **Save**, then **Activate**.

Clean-up you can do afterwards, none of it required:

- Delete the **ntfy token** credential in n8n (Credentials) if you made one.
- Deactivate the old M0 "push test" workflow that talks to ntfy.
- Delete the ntfy app from your phone.

## 4. On the iPhone

In the Bark app and in **Settings, Notifications, Bark**: allow notifications, banners and sounds. Reminders use Bark's **Time Sensitive** level, so they also show through Focus modes. Turn on **Time Sensitive Notifications** for Bark if iOS offers the switch.

## 5. Test

1. Ask: `remind me in 3 minutes to test Jarvis` (use the PowerShell test from M2). A Bark notification titled **Reminder** should arrive within a minute before that time, and there should be **no** Calendar event.
2. Say `my friend's birthday is on <a date a week from today>`. A Bark push "In 7 days: ..." should arrive at the next 9 AM India time.
3. **Test the backup.** Break the key on purpose in the Supabase SQL editor:

```sql
update jarvis.settings set value = '"wrong-key"'::jsonb where key = 'bark_key';
```

   Create another reminder 3 minutes ahead. Expect: no Bark push, but one Google Calendar event about two minutes after the attempt, and the Calendar alert on your phone. Then **restore your real key** with the update from step 2.

4. After a failed push, the reason is saved:

```sql
select value from jarvis.settings where key = 'last_push_error';
```

   With the wrong key it should say something like `HTTP 400 (code 400): ...`.

## 6. If an alert doesn't come through

Run the `last_push_error` query above.

- `no bark_key is set in jarvis.settings`: run the key `update` from step 2.
- `HTTP 400 ...` mentioning the device or key: the key is wrong. Copy it again from the Bark app.
- `HTTP 429 ...` or `5xx`: the Bark server refused or is down. The Calendar backup covers you while it lasts. Tell me if it keeps happening and I'll switch to Slack or self-hosted Bark.
- Anything else: send me the text.

## 7. Things to know

- **Bark's server (`api.day.app`) is run by Bark's author.** It is free, with no stated limits or uptime promise. That is why the Calendar backup stays.
- **Timing:** a push arrives between 0 and 60 seconds before the set time, and not after it (apart from a few seconds of delivery).
- **The backup only works while n8n is awake.** Keep the cron-job.org ping running.
- **A fired reminder stays open** until you mark it done or cancel it (M6 adds a "done" shortcut).
- Pushes are grouped under **Jarvis** in the Bark app, which also keeps a history.
- Re-check the Calendar and Gmail connections around 2026-10-28.
